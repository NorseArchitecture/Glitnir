## Confirmed facts (verified this session)

- **Postgres FK bug: fixed.** `user_lockout` now gets exactly one clean FK back to `users` — no spurious extras from unrelated navigation properties.
- **Postgres constraint naming on `users`/`user_lockout`: not a bug, a known/tested/accepted Urðarbrunnr limitation.** `NorseSnakeCaseNamingConvention.cs` deliberately skips PK/FK renaming on split entities (both principal and fragment) because `RelationalAnnotationNames.Name` is one global annotation per key with no per-`StoreObjectIdentifier` override in EF Core — renaming once would collide across fragments. Documented, tested (`Split_entity_primary_key_names_stay_distinct_per_table` etc.), commit `cbbb92c`. First time it's surfaced in a real (Himinbjörg) migration since `NorseUser` is the first production entity using `SplitToTable`.
- **SQL Server: temporal + table splitting doesn't compose.** `dotnet/efcore#26457` (buvinghausen's own Aug 5 comment is still the latest activity there — no maintainer response). Had to declare `builder.TemporalParkedOnSqlServer()` on `NorseUser` (existing Urðarbrunnr escape hatch, previously test-only) just to get a migration to generate at all. Cost: `Users` loses **all** temporal versioning on SQL Server, not just `UserLockout` — Postgres is unaffected and keeps `users` fully temporal.
- **The split doesn't achieve its stated goal yet.** Live-container test (`TemporalIdentityVersioningTests.A_failed_password_attempt_currently_versions_users`) still passes with the *old* expectation — a wrong password still mints a `users_history` row. Root cause: stock `Microsoft.AspNetCore.Identity.EntityFrameworkCore.UserStore<TUser>.UpdateAsync` does `Context.Attach(user); user.ConcurrencyStamp = Guid.NewGuid().ToString(); Context.Update(user);` — `Context.Update()` marks every mapped property Modified regardless of table, and `ConcurrencyStamp` always differs, so the temporal trigger (which compares only `users`-mapped columns) always sees a real diff and versions, no matter what actually changed.
- **Property-mutation map for stock `UserManager<TUser>`** (decompiled from the actual pinned `preview.7` DLLs, not docs):
  - `ConcurrencyStamp` — regenerated on **every** call that reaches `Store.UpdateAsync` (i.e. nearly everything).
  - `SecurityStamp` — regenerated by password changes (`ChangePasswordAsync`/`AddPasswordAsync`/`RemovePasswordAsync`/`ResetPasswordAsync`), `SetUserNameAsync`, `RemoveLoginAsync`, `SetEmailAsync`/`ChangeEmailAsync`, `SetPhoneNumberAsync`/`ChangePhoneNumberAsync`, `SetTwoFactorEnabledAsync`, `ResetAuthenticatorKeyAsync`. Untouched by `AddLoginAsync`, claim/role add-remove, `ConfirmEmailAsync`.
  - `NormalizedUserName`/`NormalizedEmail` — rewritten (same-or-new value) on every update via `UpdateUserAsync`, but only *value*-changes when `UserName`/`Email` itself changes — a value-comparing trigger won't false-fire on the rewrite alone.
  - `LockoutEnabled` — untouched by lockout/access-failed flows; only moves via `CreateAsync`'s options default or explicit `SetLockoutEnabledAsync` (still routes through full `Store.UpdateAsync`, so `ConcurrencyStamp` regenerates even for this narrow admin action).
  - Stock Identity does **not** auto-sync `UserName` with `Email` — any coupling on this platform is app wiring, not framework behavior. Worth confirming whether `NorseUserStore`/`NorseUserManager` actually do couple them, since that affects whether `UserName`/`NormalizedUserName` need special handling too.
- **`xmin` (Postgres) / `rowversion` (SQL Server) as a `ConcurrencyStamp` replacement — technically sound but unverified at runtime.**
  - No convenience method (`UseXminAsConcurrencyToken()` doesn't exist) — manual pattern: `builder.Property<uint>("Xmin").IsRowVersion()`; Npgsql's `NpgsqlPostgresModelFinalizingConvention` auto-renames the column to `xmin`. SQL Server: `.Property<byte[]>("RowVersion").IsRowVersion()`, no engine-specific convenience method either.
  - **Does** scope correctly per `SplitToTable` fragment — each fragment can get its own independently-tracked shadow property, giving correct per-table concurrency protection without a shared token. API is awkward: `IsRowVersion()` isn't reachable from inside the `SplitToTable` lambda directly (`ColumnBuilder` only exposes `HasColumnName`/`HasAnnotation`); needs the `IInfrastructure<PropertyBuilder<TProperty>>` escape hatch that `ColumnBuilder<TProperty>` implements.
  - Zero prior art found (EF Core issues/docs/samples) combining rowversion/xmin with table splitting — not exercised against a live database this session. **Wants a throwaway PoC** (matching the existing `Glitnir/poc/` pattern, e.g. `poc/ef-temporal-emission` already spikes adjacent EF Core edge-case behavior) before committing to it in `NorseUser` for real.
  - No conflict expected running both `ConcurrencyStamp`'s stock `.IsConcurrencyToken()` and xmin/rowversion simultaneously (EF ANDs all concurrency-token properties into the WHERE clause) — disabling the stock one isn't required for correctness, only to avoid a redundant check.

## Direction as of tonight (not yet decided — talk through again before spec)

- **Allowlist for what should version `users`:** `Email`/`EmailConfirmed`, `PhoneNumber`/`PhoneNumberConfirmed`, `TwoFactorEnabled`, plus future fields (FirstName/LastName/MiddleName/DateOfBirth, etc.). Everything else needs to physically move off `users` (only columns still mapped to `users` are in the temporal trigger's comparison).
- Candidates to relocate into the split table (name still open — see below): `ConcurrencyStamp`, `SecurityStamp` (already there: `PasswordHash`, `LockoutEnd`, `AccessFailedCount`). Corollary accepted: moving `SecurityStamp` alongside `PasswordHash` means a pure password change leaves **zero** trace in `users_history` — consistent with already not auditing `PasswordHash` itself, but a step further (temporal record becomes strictly "identity content changed," not "something happened to this account").
  - Still need to settle: `UserName`/`NormalizedUserName`/`NormalizedEmail`/`LockoutEnabled` — do they belong on the allowlist (audit-worthy content) or move too? Not explicitly discussed yet.
- **Concurrency guard:** replace `ConcurrencyStamp`-as-EF-token with native `xmin`/`rowversion` per fragment, specifically because a shared app-level token can only live in one physical table and leaves the other fragment's updates unguarded — pending the PoC above.
- **`UserLockout` rename:** still open. Started as "it now holds the password too, not just lockout" — now it's also picking up `ConcurrencyStamp`/`SecurityStamp`, so the name question is more pressing, not less. No candidate name discussed yet.

## Direction, continued — "no hacks," and platform-wide rowversion

Buvy's stated bar: proper table splitting with proper independent concurrency on **both** providers, `UserLockout` non-temporal, `users` temporal — no hacks like the current `TemporalParkedOnSqlServer()` (which gives up temporal on all of `Users`, not just the split-off part). Not yet resolved how to actually get there on SQL Server given `#26457` is upstream and stalled — one avenue floated implicitly but not yet confirmed/discussed with Buvy: modeling `UserLockout` as a genuinely separate related entity type (shared-PK 1:1) instead of EF's `SplitToTable` fragment mechanism, since every problem hit so far (naming convention skip, SQL Server temporal park, rowversion/xmin `TableBuilder` awkwardness) is specifically a "per-store-object metadata gap" that only exists because `SplitToTable` keeps both fragments as one entity type/one model-level annotation set. A real separate entity type would get its own independent naming, temporal, and concurrency configuration with no fragment-sharing gap at all — needs validating against Himinbjörg's actual requirements (e.g. does `UserManager`/`SignInManager` machinery tolerate lockout state living on a genuinely different entity vs. table-split fields of the same entity?) before treating this as the answer.

**Should rowversion/xmin be a platform-wide default convention, not just Himinbjörg-specific?** Buvy's question: apply it to every entity by default except pure many-to-many bridge tables (composite PK of just two FKs, no other columns) where the value is unclear since those rows are only ever inserted/deleted, not updated.

- Chassis precedent exists: `NorseModelConventions.Apply` (`Urdarbrunnr/src/Persistence.EntityFramework/NorseModelConventions.cs:50-67`) registers `IModelFinalizingConvention`s including `TemporalEntityConvention`, which walks every entity type and opts in via `ITemporalEntity`. A rowversion convention would mirror that shape (opt-out instead of opt-in). No existing "pure bridge table" marker interface anywhere in the codebase — would need to be invented from scratch if the exclusion is wanted.
- **Provider asymmetry matters here:** Postgres `xmin` is a system column every row already has — mapping it costs literally nothing, no reason to exclude bridge tables. SQL Server `rowversion` is a real 8-byte column — blanket-applying it means every table's migration diff grows a column, including bridge tables. EF Core does include concurrency tokens in `DELETE` WHERE clauses too, not just `UPDATE`, so a bridge table does get *some* protection (guards a revoke racing a stale read) — just smaller payoff than a mutable row, and only on SQL Server does that payoff cost anything.

**Downstream analytics effects (Élivágar/Sökkvabekkr — `Glitnir/docs/analytics-stack-selection-matrix.md`, `analytics-local-dev-brainstorm.md`):** WAL-based CDC (PeerDB/Debezium) → ClickHouse, bronze tables deduped on `version = LSN` (the CDC tool's own log position, not any source-side version column).
- `xmin`: invisible downstream by construction — standard Postgres logical-decoding plugins (`pgoutput`/`wal2json`) don't emit system columns, only real table columns. Zero interaction with the CDC pipeline.
- `rowversion`: **not** invisible — a real column, would get captured like any other by SQL Server CDC/Change Tracking and show up in every bronze table with no analytical meaning, needing explicit exclusion in dbt models. Schema noise, not danger, but a real cost unique to SQL Server.
- Separately flagged (not yet discussed with Buvy, just noted): Postgres's own temporal apparatus (trigger + `users_history`) and the CDC pipeline are both, functionally, "an append-only log of row versions" — one inside OLTP, one in ClickHouse's bronze layer. Not necessarily wrong (crypto-shred/erasure is a real reason to want history inside the OLTP boundary specifically) but worth being a deliberate choice once Élivágar actually gets built, not an accidental double-cost.

## Reframing — the root cause may be `NorseUserStore`, not EF/temporal machinery (leading direction as of tonight)

Buvy's read: history tables are known/accepted to be insert-only — that's *why* crypto-shredding is the erasure mechanism, not a workaround. Everything works cleanly except ASP.NET Core Identity's `UserStore<TUser>.UpdateAsync`, which unconditionally does `Context.Attach(user); user.ConcurrencyStamp = Guid.NewGuid().ToString(); Context.Update(user);` — `Context.Update()` force-marks every property `Modified` regardless of whether EF's own tracked snapshot already knows nothing else changed. In this platform's actual usage (`UserManager.FindByIdAsync` loads through the same scoped `DbContext` that later calls `UpdateAsync`), the entity is almost always already tracked by the time `UpdateAsync` runs, so the forced blanket `Update()` throws away an accurate diff EF already has.

**Proposed fix (two conditional pieces, not yet spec'd):**
1. Override `NorseUserStore.UpdateAsync` to skip the forced `Context.Update(user)` when the entity is already tracked — let normal EF change-detection at `SaveChanges()` generate the precise diff.
2. Make `ConcurrencyStamp` regeneration itself conditional on something else actually being dirty, rather than stamped on every call regardless of content.

If (2) holds, a pure lockout-only write touches nothing on `users` (not even `ConcurrencyStamp`), so EF never emits an `UPDATE users` at all and the temporal trigger never runs — solves the versioning-noise problem identically on **both** providers, no xmin/rowversion/per-fragment concurrency or entity-vs-`SplitToTable` redesign required.

**Open risk, not yet resolved:** stock Identity's blanket-overwrite behavior is defensive — it can't assume every caller passes a tracked entity (a genuinely detached `NorseUser`, e.g. from some future stateless/API path, would need the current Attach+Update-everything fallback preserved). The override needs to branch on `Context.Entry(user).State`, not just delete the forced `Update()` call outright. Also needs auditing: does anything currently, even accidentally, *rely on* the blanket-overwrite behavior (e.g., something that mutates `user` in memory outside EF's tracking and expects `UpdateAsync` to persist it regardless)?

**Where this leaves the rest of tonight's exploration:** if this pans out, it likely makes the xmin/rowversion-per-fragment work and the `SplitToTable`-vs-separate-entity question *unnecessary* rather than complementary — a much smaller, more surgical fix than either. Worth spiking this first before spending spec effort on the wider redesign.

**Why the `SplitToTable`-vs-separate-entity fork is settled in favor of `SplitToTable` (not just deferred):** Buvy's priority is keeping `NorseUser` as close to drop-in `IdentityUser<Guid>`-compatible as possible. A genuinely separate `UserLockout` entity type would surface a second entity + navigation to anything treating `NorseUser` as a normal Identity user — exactly the consumer-visible surface change `SplitToTable` avoids (it's purely a persistence-layer concern, invisible outside the DbContext). So the entity-splitting alternative is out, not just parked; the `UserStore` fix is the path, and it keeps `SplitToTable` as the physical mechanism.
